# PREREG: Morpho Blue (Base) replay: how often are liquidations won in the same block as an oracle price update? — written 2026-11-22 before any Morpho gap data

Question: Morpho Blue on Base passed the registered venue test (`PREREG_LIQ_MORPHO_20261121.md`: bonus is large and fragmented). Can a bot detecting the oracle update (and not co-located) still reach a meaningful share, or are most liquidations backrun in the same block as the price update, as on Aave (64–78%)? Same method as `PREREG_LIQ_REPLAY_20261121.md`.
Data: Morpho Base `Liquidate` events (months 17–23, 2026-04-01..2026-10-31, eligible = bonus > USD 50 with valid prices), deterministic sample every k-th by (block, tx, user) for about 400 (stage 2) and every 4th of those (stage 1). Market id from the raw shard files joined on (tx, user, block). Per event: market oracle address from `idToMarketParams(id)` (word 2); the oracle's `BASE_FEED_1()`, `BASE_FEED_2()`, `QUOTE_FEED_1()`, `QUOTE_FEED_2()` (Chainlink-style feeds; zero address = unused); each feed's `aggregator()` if it answers, else the feed itself. UPDATE = any log emitted by one of those addresses. Oracles that do not expose these getters are unresolved (excluded, counted).
Definitions (as in the Aave replay): GAP G = B_w − last block <= B_w with an update log from any resolved feed of the market's oracle, searched in the 1,000 blocks before (Base endpoint limit; about 33 minutes; none found = "no update in window" and counts as reachable). IDEAL arm L = 2 blocks (0.3 s detection, 2 s blocks); post-hoc table of R for L = 1, 2, 3, 5, 8, 12. NULL: one seeded random block per event on the same feeds. R = share of resolved events with G > L; R_value = bonus-weighted. Feed check: if more than 50% of resolved events show no update in the window the market set is declared unresolved and the result "not credible".
Rules: Stage 1 pilot (KILL-ONLY): pooled R < 3% AND R_value < 3% → stop, venue is a same-block backrun market. Stage 2: DROP the fast-bot hypothesis for Morpho if R < 5% AND R_value < 5%; PLAUSIBLE if R >= 10% AND R_value >= 10%; otherwise MARGINAL. Descriptive: split by month (Jun 2026 vs Oct 2026 vs other months, the two stress months), by oracle (top 5 oracles), share of resolved events.
Costs: none. Output `scripts/liq_morpho_replay_20261121.py` → `docs/jx_runs/liq_morpho_replay_20261121.txt` (run twice, identical), ledger rows. A pass is again only a necessary condition (assumes instant detection).

## Addendum 1 (2026-11-22): stage-1 pilot result and feed diagnostic
Stage-1 pilot (`docs/jx_runs/liq_morpho_replay_20261121_stage1.txt`): 100 sampled events, 96 with resolved oracle feeds on 11 of 13 markets, but the feed check FAILED (68% of resolved events show no update in the 33-minute window; the registered outcome is "not credible, no verdict"). Pattern seen: all 26 October 2026 events fall within 1 block of an update (gap <= 1: 100%), all 53 June 2026 events show no update at all. That is either a resolution problem for the June markets or genuinely stale/non-Chainlink oracles. No kill and no verdict follow from it. A diagnostic job (`liq_morpho_replay_diag`) prints per market the oracle, feed and aggregator addresses and the number of logs in the prior 20,000 blocks, to decide whether resolution can be fixed (HOW). If it can, stage 2 will run with the fix and the same rules; if not, the Morpho replay is reported as not resolvable and the shadow arm becomes the way to measure speed.

## Addendum 2 (2026-11-22): diagnostic result and fix (HOW; rules unchanged)
Diagnostic (`docs/jx_runs/fetch_public_44971704532.txt`): for October 2026 events the resolved feeds emitted 69–279 logs in the prior 20,000 blocks, but for April–June 2026 events several markets' feeds emitted 0 logs. Cause (most likely, measured as a pattern, not proven): `aggregator()` was read at the latest block, but Chainlink proxies change aggregator contract over time (phases), so older events looked for logs at a contract that did not yet exist. Fix: every proxy's earlier phase aggregators (`phaseId()` / `phaseAggregators(i)`) are now included in the address list. Three of 13 markets use oracles that expose no `BASE_FEED_*`/`QUOTE_FEED_*` getters (custom oracles): unresolved, excluded, counted.
The first pilot file is kept as `liq_replay_gaps_s1_morphobase_v1_latest_aggregator_only.parquet` (not used for any verdict); the pilot is re-run with the fix. Stage-1 kill and all stage-2 rules are unchanged.

## Results (2026-11-22; `docs/jx_runs/liq_morpho_replay_20261121.txt`, re-run identical; command `uv run python -I scripts/liq_morpho_replay_20261121.py 2`; stage 1 `..._stage1.txt`)
397 sampled Morpho Base liquidations (months 17–23, bonus > USD 50), 386 with resolved oracle feeds on 18 markets (97%; feed check passed: 1% show no update in the window; three markets use custom oracles and are unresolved). Gap to the latest update of the market's oracle feeds:
- same block as an oracle update: 93.8%; within 1 block: 97.9% (random blocks: about 0.3%);
- reachable for a watcher detecting 2 blocks after the update (IDEAL arm): 2.1% of events, 0.8% of bonus value; at 8 blocks 0.8% / 0.3%;
- by month: June 2026 (215 events) 0.0% reachable, October 2026 (107) 0.0%, the other months (64 events) 12.5% by count / 10.5% by value.
**Registered verdict: DROP the fast price-triggered-bot hypothesis for Morpho Base at block-level latency (R < 5% and R_value < 5%).** The two stress months that carry most of the money are entirely same-block. Limits: block-level gaps cannot see inside a block, so a bot reading Base's 200 ms pre-confirmed "flashblocks" could still race for same-block events; this test does not cover that and cannot rule it in or out. The shadow test for Aave is also block-level. A pre-registered flashblocks-latency arm is the only remaining way to test speed.
